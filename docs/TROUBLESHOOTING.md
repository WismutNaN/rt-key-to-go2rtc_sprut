# Первый запуск и диагностика

## Чек-лист первого запуска

1. На целевом Linux-сервере установите Docker Engine и Compose plugin.
2. Выполните `./install.sh --server-ip <LAN-IP-сервера>` и введите Bearer Token скрытым вводом. По умолчанию используется малонагруженный профиль `video=copy`, `audio=pcmu`.
3. Убедитесь, что установщик вывел каждую ожидаемую камеру, её UID, постоянный RTSP URL и snapshot URL.
4. Выполните `./manage.sh status`. Controller должен быть `healthy`; сразу после старта допустим короткий период `starting`.
5. Выполните `./manage.sh check-streams`, затем откройте каждый RTSP URL в VLC. Проверьте изображение и наличие аудиодорожки.
6. Добавьте RTSP URL в SprutHub как прямую камеру, а HTTP URL — как snapshot. ONVIF не нужен.
7. Выполните `./manage.sh refresh` во время просмотра. Изображение может кратко переподключиться, но контейнер go2rtc и RTSP endpoint не должны останавливаться.
8. Перезапустите только controller и затем только go2rtc. После восстановления ссылки и имена должны остаться прежними.

Docker не запускался на машине разработки проекта. Этот чек-лист является обязательной проверкой реальной сети, токена, кодеков и архитектуры процессора сервера.

## Камеры не появились

Выполните:

```bash
./manage.sh status
./manage.sh logs
```

Типовые причины:

- Bearer Token истёк или скопирован вместе со словом `Bearer`/пробелами — выполните `./manage.sh set-token`;
- оба неофициальных API изменили схему — логи покажут отказ обеих versioned strategies;
- Ростелеком вернул новый домен media host — добавьте только доверенный suffix в `ALLOWED_STREAM_HOST_SUFFIXES` и выполните `./manage.sh refresh`;
- медленное соединение не укладывается в probe — осторожно увеличьте `RTSP_PROBE_TIMEOUT_SECONDS` в `.env`;
- DNS или исходящий HTTPS заблокирован на сервере.

Не публикуйте `.env`, каталог `secrets/`, state JSON и полный source из
отладчика: они содержат действующие credentials или временные токены.

## Поток виден в списке, но не воспроизводится

Обычный Docker healthcheck выполняет только RTSP `OPTIONS` и не запускает
FFmpeg. Команда `./manage.sh check-streams` выполняет `DESCRIBE` каждой камеры и
временно запускает её upstream. Сообщение `did not pass RTSP/upstream probe`
означает, что имя уже есть в go2rtc, но источник не вернул пригодное media
description.

Проверьте по порядку:

1. `./manage.sh refresh` — получить новый streamer token;
2. `./manage.sh status` — убедиться, что `expires_at` находится в будущем;
3. `./manage.sh logs` — проверить безопасную ошибку controller;
4. при необходимости `./manage.sh logs-media` — посмотреть FFmpeg/go2rtc, не публикуя вывод до удаления возможного upstream URL;
5. заменить Bearer через `./manage.sh set-token`, если status показывает authentication failure.

## Длительный зелёный экран

В старом профиле входные временные метки принудительно заменялись системным
временем, а затем видео программно перекодировалось. Для H.264 с B-кадрами это
могло давать неверный порядок кадров; один 720p encoder также способен полностью
занять слабый CPU.

Примените поддерживаемый профиль повторным запуском установщика:

```bash
./install.sh
```

После этого используйте в SprutHub URL без `_1280x720`. Обновлённый input-профиль
не подменяет timestamps системным временем, а `video=copy` полностью исключает
video decode/encode на сервере.

## Как выбрать нагрузку и разрешение

По умолчанию `./manage.sh show` печатает одну пару RTSP/snapshot без суффикса.
Видео передаётся как есть и почти не нагружает CPU. Это лучший вариант для
слабого сервера.

Любое изменение разрешения требует полного decode → scale → encode. Меньшее
разрешение экономит сеть и ресурсы SprutHub, но не является способом снизить
нагрузку Docker-сервера относительно `video=copy`.

Поэтому поддерживаемая установка не создаёт ссылки `_1280x720` и `_640x360`.
Используйте только бессуффиксные RTSP и snapshot URL, которые печатает
`./manage.sh show`. Snapshot декодирует ровно один keyframe и кэширует результат.
Время кэша меняется параметром
`--snapshot-cache`, например `--snapshot-cache 60`.

## Видео есть, звука нет

Исходный поток содержит AAC-LC, 48 kHz, mono. Шлюз выдаёт PCMU/8000 mono — тот
формат, который SprutHub сам выбрал в приведённой диагностике при получении PCMA.

Если VLC воспроизводит звук, а SprutHub видит название codec, но не показывает
управление звуком, шлюз передаёт аудиодорожку. В официальной документации
поддержка RTSP-камер в SprutHub отмечена как beta и прямо допускается частичная
работа без звука; такой результат следует проверять на версии самого хаба.

## Snapshot не открывается

Ссылка имеет вид:

```text
http://spruthub:<пароль>@<LAN-IP>:8080/snapshot/<stream-name>.jpg
```

Проверьте её обычным браузером или HTTP-клиентом. Первый запрос может занять
несколько секунд: он лениво запускает upstream и получает первый кадр. Ответ 401
означает неверные credentials, 404 — неизвестную/ещё не проверенную камеру,
502 — временную ошибку upstream, 503 — заняты все ограниченные snapshot workers.
RTSP при ошибке snapshot не перезапускается.

## Истёк основной Bearer Token

Streamer tokens обновляются автоматически по JWT `exp`, но основной Bearer Token не восстанавливается автоматически. Выполните:

```bash
./manage.sh set-token
```

Будет пересоздан только controller. go2rtc и постоянный RTSP-сервер продолжат работать с последним source, пока тот действителен.

## Безопасность LAN

Порт 1984 не публикуется на сервер. Порты 8554 (RTSP) и 8080 (только snapshot)
защищены отдельным случайным паролем, но по умолчанию слушают LAN. Если сеть не
полностью доверенная, ограничьте firewall сервера так, чтобы оба TCP-порта были
доступны только с IP SprutHub. Проект намеренно не меняет firewall автоматически.

## Откат

`./manage.sh down` останавливает контейнеры, сохраняя `.env`, Bearer Token в
`secrets/rtkey_access_token` и Docker volume. Не используйте
`./uninstall.sh --purge`, пока не убедились, что состояние и постоянное
соответствие UID → stream name больше не нужны.
