# ADR-0006: DDD-lite и границы расширения

**Дата**: 2026-09-06
**Статус**: Принято

## Контекст

API Ростелекома уже изменил endpoint и форму полей. В будущем проект может управлять домофонами, шлагбаумами и звонками, однако текущая задача остаётся небольшим видеошлюзом для одного пользователя.

## Рассматриваемые варианты

1. **Один класс RTKey со всеми методами** — быстро сейчас, но связывает видео, доступ, звонки, HTTP и состояние.
2. **Полный DDD с микросервисами и event bus** — хорошие границы, но несоразмерная эксплуатационная сложность.
3. **Модульный монолит DDD-lite с ports/adapters** — направленные зависимости и отдельные bounded contexts без преждевременного распределения.

## Решение

Выбрали **модульный controller с dependency rule `domain ← application ← infrastructure/interfaces`**. Video Gateway и opt-in Access Control реализуются как независимые bounded contexts в одном процессе; Intercom Calls остаётся отдельным будущим контекстом. Источник Bearer Token, часы и типизированные ошибки образуют минимальный shared kernel. Изменения API поглощаются strategy-adapters и anti-corruption mapping.

## Последствия

**Становится проще**: заменить endpoint/схему Ростелекома, JSON-хранилище или go2rtc, тестировать use cases без сети.
**Становится сложнее**: больше небольших файлов и явная сборка зависимостей.
**Закрывает дверь на**: циклические импорты, общий `Device` без ясных инвариантов и mega-interface для всех функций Ростелекома.
