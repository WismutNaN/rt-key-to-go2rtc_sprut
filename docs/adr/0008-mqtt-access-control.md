# ADR-0008: MQTT для кнопок открытия SprutHub

**Дата**: 2026-09-07
**Статус**: Принято

## Контекст

SprutHub должен видеть домофоны и шлагбаумы как готовые устройства. Прямой вызов Ростелекома из сценария дублирует provider-логику и раскрывает Bearer Token, а отдельный HomeKit bridge заметно усложняет развёртывание.

## Рассматриваемые варианты

1. **JavaScript-сценарий SprutHub → Ростелеком** — без нового протокола, но Bearer и недокументированный API оказываются в каждом сценарии.
2. **HTTP gateway + виртуальные кнопки** — секрет Ростелекома изолирован, но каждое устройство создаётся вручную.
3. **Встроенный MQTT broker SprutHub** — retained discovery и стандартные Switch-устройства.
4. **HomeKit bridge** — нативные аксессуары, но pairing, mDNS и дополнительное состояние несоразмерны задаче.

## Решение

Выбран **MQTT adapter в существующем controller**. Отдельный broker/container не запускается: используется встроенный broker SprutHub. Функция opt-in через `ACCESS_CONTROL=mqtt`; по умолчанию она выключена.

SprutHub не подставляет regex-группы в имена устройства и сервиса. Поэтому после
обнаружения каталога controller генерирует один JSON составного устройства. Каждая
точка становится статически именованной Switch service с exact MQTT topics.
Retained topic `access/catalog` используется только для обнаружения устройства.
Нестандартная динамическая характеристика `Name` не используется.

## Последствия

**Становится проще**: автоматическое обнаружение всех точек доступа, сценарии SprutHub по обычному Switch, замена provider API без изменения SprutHub.
**Становится сложнее**: нужно один раз включить broker, создать MQTT-controller и импортировать сгенерированный шаблон.
**Закрывает дверь на**: хранение Bearer в SprutHub, произвольный публичный HTTP open и retained-команды открытия.
