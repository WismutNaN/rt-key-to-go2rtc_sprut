# ADR-0007: Ленивый медиатракт и профиль совместимости SprutHub

**Дата**: 2026-09-06
**Статус**: Принято

## Контекст

Исходные потоки Ростелекома содержат H.264 и AAC-LC, но у видео наблюдаются
скачки и повторы DTS. Передача H.264 без изменений почти не нагружает CPU, однако
на части клиентов приводит к длительному зелёному экрану. Постоянное
перекодирование четырёх камер устранило бы timestamps, но бессмысленно расходовало
бы ресурсы, когда камеры никто не смотрит.

## Рассматриваемые варианты

1. **Всегда `video=copy`, `audio=copy`** — минимальная нагрузка, но сохраняет
   нестабильные timestamps и не решает совместимость аудио SprutHub.
2. **Постоянный FFmpeg для всех камер** — предсказуемый media stream, но высокая
   фоновая нагрузка и лишние подключения к облаку.
3. **Ленивый стабильный профиль** — H.264 CFR и PCMA создаются только при наличии
   RTSP/snapshot consumer; для стабильных камер разрешён per-UID `copy`.

## Решение

Выбрали **ленивый стабильный профиль**. go2rtc хранит source без активного
FFmpeg-процесса, а при подключении consumer запускает нормализацию H.264 в CFR с
коротким GOP и преобразование аудио в PCMA. Автоматический healthcheck использует
только RTSP `OPTIONS`; `DESCRIBE` всех upstream выполняется при смене token и по
явной команде `check-streams`. Неизменившийся source повторным PATCH не заменяется.

## Последствия

**Становится проще**: SprutHub получает стабильные timestamps, а простой системы
не расходует CPU на media.

**Становится сложнее**: во время просмотра используется программное H.264-
перекодирование; первый кадр появляется после ленивого запуска FFmpeg.

**Закрывает дверь на**: постоянную фоновую аналитику внутри этого проекта. Для
Frigate или архива отдельный постоянный consumer должен подключаться осознанно.
